# AI 全自动小说工作流

## 1. 产品目标

Amy Novel 的目标不是提供一个续写按钮，而是成为可审计、可暂停、可恢复的小说生产
Agent。作者负责提供 idea、题材、篇幅、审美和禁止事项，并在关键节点判断结果是否符合
心意；Agent 负责从设定到正文的完整生产流程。

作者始终拥有最终决定权。AI 的规划、正文与事实提取先作为候选保存，只有作者接受后才
进入正史。全自动表示流程能够自动运行，不表示 AI 可以绕过作者修改正史。

## 2. 完整流水线

```text
Idea / 题材 / 篇幅 / 作者边界
  → 故事圣经：主题、世界规则、文风、禁止事项
  → 人物体系：主角、核心配角、酱油人物、龙套名称
  → 名称体系：题材名称池、别名、查重、已用名登记
  → 场景库：功能、氛围、视觉锚点、常驻人物、危险等级、复用规则
  → 结构规划：分卷目标、每章标题、每章章纲、场景与伏笔安排
  → 逐章循环：Context Pack → 正文 → 检查 → AI 审稿 → 候选稿
  → 作者验收：接受 / 拒绝 / 修改 / 重生成
  → 接受后：不可变版本 → 事实提案 → 作者确认 → 正史更新
  → 下一章
```

### 2.1 规划页十步审核向导

规划页面一次只展示一个当前任务，Amy 的提示和追问直接嵌入步骤，不再同时展示章节树、
四个生成入口和独立聊天栏。步骤顺序固定为：

1. 创作目标：题材、目标读者、篇幅、文风、禁忌；
2. 核心创意：卖点、主线矛盾、主角目标与失败代价、结局方向；
3. 世界观与故事圣经；
4. 主角及核心人物；
5. 配角、反派、酱油人物、龙套与名称池；
6. 地点、势力、物品和可复用场景库；
7. 滚动路线与当前十章；
8. 当前策划包与前置设定增补提案审核；
9. 当前范围一致性检查与人工确认；
10. 当前范围连续正文生成。

缺失创作简报字段时，Amy 每次只追问当前最先缺失的一项。前两步保存的作者简报进入
故事圣经规划 Prompt，特别是禁忌不能由模型擅自改变。每一步都必须由作者确认才能解锁
下一步；返回编辑不会自动修改正史。步骤 7–10 按十章周期循环，完整规则见
`ROLLING_STORY_HARNESS.md`。全书路线只保存宏观阶段，未来未规划章节保留空槽位；每次
只详细生成当前范围的标题、章纲、人物、场景、道具、技能和伏笔安排。

创作简报和审核进度是正式作品数据，由 Web/Electron 的同一 `PlatformPort` 契约保存，
并进入项目备份。修改上游内容会自动撤销相关步骤及其后的确认：故事圣经从第 3 步、
人物从第 4 步、场景实体从第 6 步、分卷从第 7 步、章纲从第 8 步重新审核。第 9 步没有
确认时，创建正文批次的数据层接口直接拒绝请求，不能靠手输路由绕过。

结构规划必须恰好覆盖作品设定的目标章节数。每章都必须具备独立章节标题和非空章纲，
章纲至少说明事件、出场人物、复用场景、冲突、结果、伏笔和章末钩子。规划不完整时不
允许进入整书自动生成。

超长作品不能永远依赖一次模型响应。当前版本先用完整章数门禁防止半截目录落库；
Workflow Runner 阶段将按“先生成卷级配额，再按卷分批生成章节标题与章纲，最后全书
合并校验”执行。单次结构调用的规模上限应通过真实模型评估决定，而不是写死一个理想值。

## 3. 人物与名称规则

| 层级 | 数量建议 | 设定强度 | Context Pack | 正史追踪 |
| --- | ---: | --- | --- | --- |
| 主角 `protagonist` | 1 | 身份、性格、目标、秘密、语言习惯、成长弧线 | 常驻 | 完整 |
| 核心配角 `support` | 3–6 | 目标、关系、秘密、阶段弧线 | 常驻或按章纲 | 完整 |
| 酱油人物 `recurring` | 6–15 | 一句话定位、出现条件、与主角关系 | 章题/章纲提及时 | 轻量 |
| 跑龙套 `extra` | 按需 | 只登记名字和题材风格 | 不注入 | 不追踪 |

所有正式采用的主角、配角、酱油和龙套名称都写入名称池 `usedNames`。新角色必须同时与
实体名称、别名和已用名称查重。龙套升级为反复出场人物时，必须先转成 `recurring`
角色卡，不能依靠模型在正文中自行记忆。

## 4. 场景设定与复用

场景卡不是地点简介，而是可重复调用的叙事资产，至少包含：

- 叙事功能：选择、奖励、冲突、休整、揭密等；
- 感官氛围：视觉、听觉、气味和情绪基调；
- 视觉锚点：3–5 个重复出现时保持不变的标志；
- 常驻人物、危险等级和空间限制；
- 名称与别名，供章题和章纲匹配。

只有章题、章纲或场景拆分提及的场景卡进入当前 Context Pack。重复场景必须保留视觉
锚点，不允许同一地点在不同章节无解释地改变布局。

## 5. 逐章生成与候选链

同一本小说默认串行生成。第 N 章可以读取本批次已生成但尚未接受的前章候选稿，形成
“候选链上下文”；该内容明确标记为非正史，只用于保持当前批次的情节连续性。作者拒绝
或重生成前章后，后续受影响章节应标记为需要复核。

批次遵守以下规则：

1. 单个批次只允许一个执行器，避免重复请求和预算竞争。
2. 每章调用前按剩余 Token 硬预算限制 `max_tokens`；不足 500 Token 时安全暂停。
3. 429/5xx 等可重试错误使用 `Retry-After`，否则按 1、2、4、8 秒指数退避，最长 30 秒。
4. 401/403 等不可重试错误立即失败，等待作者修正配置。
5. 候选稿未接受前，任何事实提案都不能写入正史。
6. 接受候选稿不等于完成本章：其事实提案必须逐项接受或拒绝，全部处理后才放行下一章。
7. 周期封存是第二道硬门禁，范围内任一已接受候选仍有待处理提案时必须拒绝封存。

## 6. 作者检查点

Autopilot 提供三种运行模式：

- 关键节点暂停（默认）：圣经、人物、场景、卷章规划分别等待作者确认，然后生成正文；
- 每章暂停：每章候选稿等待作者处理后再继续；
- 全自动候选：连续生成全部候选稿，但不自动接受、不自动写正史。

自动接受属于可选能力，默认关闭。即使开启，也必须同时满足确定性检查无 error、
AI 审稿无 error、字数达到目标 90%，并保留可回滚版本。

### 6.2 渲染层自动审阅（AN-026 实现，AN-028 加固）

作者可在生成工作台（或生成配置页创建任务时）显式开启「自动接受并连续创作」。
这是**作者委托审阅**：开关本身即作者的接受授权，正史门禁与写入路径不变，只是
确认动作由渲染层定时器代为触发。运行语义：

- 每轮（2 秒）按顺序处理当前批次最早的待审章节：接受候选稿 → 接受全部正史建议
  （`source=ai_candidate`）→ 恢复批次写下一章（相当于点击“继续生成下一章”）；
- 质量门：存在未解决的 error 级检查问题（findings），或 AN-027 确定性全局校验
  发现 error（引用悬空等数据完整性问题）时立即暂停并交还人工，不自动接受；
- 自动停止条件：本批次完成、候选稿被拒绝、或连续 3 轮无进展失败；每次自动
  动作都以 `auto_review` 阶段事件留痕到批次活动日志；
- 开关持久化（`amy-novel:auto-review`，AN-028）：刷新/重启后自动恢复断点续跑；
  各类自动停用会同步清除持久化，重启后不会复活已停用的模式；
- 新出场角色（AN-028）：自动路径接受圣经外角色的状态建议时，先建最小实体卡
  （summary 注明自动建档与首出章节）再写状态；人工路径仍要求先在圣经建档；
- 单条容错（AN-028）：某条建议处理失败不阻断其余建议，活动日志注明待人工
  处理；仅当一轮零进展（全部失败）才计入连续失败次数；
- 状态可见（AN-028）：批次暂停（手动/预算耗尽）、排队未启动、正文生成中，
  均写入自动审阅横幅，不再出现“开关亮着却毫无动静”的静默假死；应用重启导致
  运行器丢失（批次停在 running 但无任务推进，或任务卡 generating 超 5 分钟）时
  自动重新接管续跑；
- 批次互斥（AN-028）：同一作品同时只允许一个未完结批次（双端同规则），排队
  批次可在工作台停止；一次性章数由生成任务的章节范围决定，Token 硬预算与
  暂停恢复照常生效。

与 Workflow Runner 的分工：Runner 编排规划阶段与批次创建（主进程，可断点恢复）；
自动审阅只负责审阅动作的代执行（渲染层），不创建批次、不代签十步向导确认。
字数 90% 门槛暂未接入自动审阅（候选字数不足时不阻断），与 AN-023 审查重写联动
时一并处理。

### 6.3 全自动巡航（AN-035，已实现）

两段式模型的第二段：地基期作者用 6.1/6.2 的逐项流程精控；信任建立后可在
规划页第 10 步开启「全自动巡航」，一个按钮循环跑到目标章数。循环体：
周期规划（proposal_review 暂停点自动接受全部设定提案）→ 建批次
（autopilot 模式）→ 正文连写与正史建议自动接受（联动 6.2 自动审阅）→
周期封存（实际结束状态由正史记忆确定性起草，AN-027 全局校验 error 阻断）→
下一周期。停止与恢复：到达目标章数收工；运行失败、批次 Token 预算耗尽、
全局校验 error、连续 3 次失败都转为 paused 并记录原因，「继续巡航」从中断
处续跑；开关持久化，应用重启自动重挂载（paused 保持暂停，作者点续跑）。
不设总预算上限（用户定案）；不卡第一卷封存，十步向导完成即可开启（用户定案）。

### 6.1 Runner 运行语义（实现约定）

Workflow Runner 复用现有规划器（`generateNovelPlan`）和 BatchRunner，不另建调度框架。
运行状态持久化在 `workflow_runs`，编排逻辑在 `src/application/run-workflow.ts`：

1. **阶段推进**：`bible → cast → scenes → structure → generation`。规划阶段失败按
   `maxPhaseRetries`（默认 2，含首次共 3 次完整调用）重试，耗尽后标记失败并保留错误；
   从失败状态恢复视为作者决定再试一次，重试预算随之重置。
2. **检查点暂停**：checkpoint 模式在每个规划阶段完成后暂停等待作者审核；存在待审
   设定提案时三种模式一律暂停（proposal_review）——包括全自动候选，因为结构规划产出
   的增补提案影响正文方向，未审核前不进入正文生成。
3. **代签确认**：非 checkpoint 模式在提案全部处理完毕后，由 Runner 代签十步向导的
   九步确认以满足数据层门禁；checkpoint 模式永不代签，作者必须在向导中逐步确认。
   代签等价规则：当前范围内设定提案全部接受或拒绝，视为规划已获作者确认。
4. **正文批次**：一次运行只携带一个滚动批次的章节范围。autopilot 模式关闭单章审批
   门禁以连续生成全部候选稿；checkpoint / chapter 模式沿用单章审批。批次完成不等于
   入正史：候选稿仍需作者逐章接受，事实提案仍按单章审批硬门禁处理。
5. **状态收敛**：批次状态到运行状态的映射（完成 / 失败 / 等待章节审核 / 暂停）由
   `src/domain/workflow-run.ts` 的 `workflowRunUpdateFromBatch` 单点维护。Web 端批次在
   恢复调用内同步执行完毕，恢复返回时即收敛；Electron 端批次在主进程后台执行，运行
   状态由批次广播事件（`batch_completed` / `batch_paused` / `awaiting_review`）驱动收敛。
6. **断点恢复**：曾在规划检查点（阶段或提案审核）暂停的运行，恢复时必须重新校验
   提案并重走代签判定，不能直接创建正文批次；已进入正文阶段的运行按批次状态收敛。
   封存周期后由作者为下一个十章范围启动新运行，运行本身不跨周期循环。

## 7. 真实 10–20 章评估门槛

在实现 Workflow Runner 前，必须用真实模型完成至少一次 10–20 章连续生成，并记录：

| 维度 | 通过标准 |
| --- | --- |
| 章节完整性 | 章节标题、章纲、正文一一对应，无缺章和重复章 |
| 人物一致性 | 主角身份/能力无硬冲突；核心配角无无故改名；龙套不撞名 |
| 时间线 | 已发生事件顺序无倒置，跨章时间跳跃有解释 |
| 伏笔 | 计划埋设与回收可定位；无提前泄露关键答案 |
| 场景复用 | 重复地点保留名称、空间关系和视觉锚点 |
| 候选链 | 后章正确承接前章候选结尾，拒绝前章时能识别受影响章节 |
| 预算与恢复 | 不突破硬预算；429/503 可退避；暂停后从未完成章恢复 |
| 正史门禁 | 未接受候选稿的事实不能进入正史 |

评估结果保存为作品级报告，至少列出模型、参数、Prompt 指纹、Token、Finding 数量、人工
判定和失败样例。未达到门槛时先修底层生成链路，不进入 Workflow Runner 开发。

## 8. 实施顺序

1. 正史门禁；
2. Web/Electron 共用模型请求规则；
3. 限流退避、单执行器和硬 Token 预算；
4. 批次候选链上下文；
5. 真实 API 连续生成 10–20 章并完成评估；
6. 复用现有规划器和 BatchRunner 实现 Workflow Runner。

前四项是 Workflow Runner 的前置可靠性基线。第五项需要作者提供真实模型配置并明确
同意产生 API 费用。第六项不另建通用 Agent 框架，只负责编排现有阶段与持久化检查点。
