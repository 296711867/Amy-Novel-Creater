# 真实 API 滚动十章闭环评估（2026-08-30）

## 1. 目的与结论

用真实模型跑完路线图要求的第 7 步验证：`1–10 章规划 → 正文生成 → 正史确认 →
记忆回写 → 封存周期 → 11–20 章规划`。

**结论：闭环已跑通。** 周期状态机、范围门禁、提案审核、正史门禁和记忆回写在真实
模型下行为正确；同时暴露出 JSON 稳定性、事实提案 payload 形状、实体重复和下一周期
规划上下文缺口四类真实问题，其中两类解析边界已在本轮修复。

- 模型：智谱 GLM Coding Plan（`GLM-5.2`，`open.bigmodel.cn/api/coding/paas/v4`）
- 测试作品：《滚动十章评估·雾灯航路》，玄幻，20 章 × 800 字（评估用小体量，状态机与产品一致）
- 运行方式：`tests/e2e/rolling-cycle.e2e.test.ts`，默认跳过，`AMY_E2E_REAL=1` 时执行。
  驱动与产品同构：规划调用镜像 `novel-ipc.ts` 处理器，正文生成复用 `BatchRunner`，
  提案审核复用 `reviewPlanningProposal`，接受与记忆回写镜像 renderer store。状态落
  临时 SQLite 库（仓库外），可断点续跑。

## 3. JSON 稳定性（本次最大噪声源）

规划共 12 次调用，6 次失败后重试成功，失败分四类：

| 失败形态 | 次数 | 根因与处置 |
| --- | --- | --- |
| `profile` 字段值为数组/数字 | 1 | schema 只收 `Record<string,string>`。**已修**：解析层统一归一为字符串（`src/domain/planning.ts`） |
| 卷名带范围后缀（`卷一·灯油是记忆（1-3章）`）而章节引用裸名 | 3（连续） | **已修**：卷名匹配归一化（去括号范围、统一分隔符，`normalizeVolumeTitle`，`assertCompleteStructurePlan` 与 `apply-novel-plan` 共用），含域测试 |
| 裸 JSON 语法错误（字符串内未转义引号等） | 3 | 不可静态修复。失败已按设计落 `planning_runs`（原始响应、错误、Token），重试可恢复 |
| 尾章标题/章纲为空串；JSON 截断 | 2 | 列表尾部长输出质量衰减；重试可恢复 |

建议下一步（对应 `ROLLING_STORY_HARNESS.md` §7 已规划未实现的项）：

1. 实现一次低温 JSON 修复调用：结构完整性失败时，把原始响应连同解析错误发回模型
   低温修复，最多一次，原始运行记录不覆盖；
2. 评估 bigmodel `response_format` 结构化输出对 GLM-5.2 的可用性；
3. 提示词层把 `visualAnchors`、`profile` 等数组字段的示例写得更显式（本次两处语法
   错误都发生在把数组写成带引号串列时）。

另确认：GLM-5.2 默认输出 `reasoning_content`，产品以 `thinking: {type:"disabled"}`
规避后正文与 JSON 均正常。

## 4. 事实提案（记忆回写）质量

72 条提案中 40 条（55%）因 payload 形状被 Zod 拒绝，直接导致封存摘要贫乏
（6 条状态里 5 条"目标：无；持有：无"）和伏笔表为空：

| 类别 | 数量 | 失败根因 |
| --- | --- | --- |
| `foreshadow` 25/25 全拒 | 25 | `status` 为自由文本：`未回收`、`open`、`unresolved`、`未解`、`未揭示`、`未应验`、`进行中`。schema 要求 `planned/planted/developing/resolved/abandoned` 枚举，且 `fact_extraction` 提示词未列出合法值 |
| `character_state` 15/21 被拒 | 15 | `summary` 缺失（提示词写"可含"）；`inventory`/`knowledge`/`goals` 有时写成字符串而非数组 |
| `timeline` 26/26 全成 | 0 | — |

修复方向（下一循环）：

1. 解析层容错：字符串→单元素数组（或按「、」拆分）、`summary` 缺失时回退 `title`；
2. `foreshadow.status` 建立中文语义映射（未回收/open/unresolved→`developing` 等），
   无法映射时回退 `planted`；
3. `fact_extraction` 提示词写明字段类型与 `status` 枚举；
4. 与路线图第 2 项「批次记忆审核硬门禁」合并：封存前强制检查事实提案处理率，
   高拒绝率时提示作者，避免"无未决伏笔"这类失真封存。

## 5. 一致性与连续性评估（人工核对）

- **第 10→11 章衔接矛盾（关键缺口实证）**：第 10 章结尾，洛沉璧残念消散并给出
  「哑言塔塔魂将被崔衡拆走、西南三十里银帆拆塔中」的紧迫钩子；而第 11 章章纲让
  林昭在归萤塔外**再次引出洛沉璧**，拆塔事件完全未被承接。原因：`rolling_structure_
  planning` 提示词只含圣经、实体目录与当前范围空白槽位，**不含**上一周期
  `actualClosingState`、人物动态状态、时间线、伏笔和已接受正文摘要。11–20 规划
  是"看着实体卡重新发明"，而不是"接着正史写"。
- **称呼漂移**：同一反派在实体库有「守灯人旧部首脑·崔衡」「崔衡」双卡，正文用
  「崔衡/督灯使」，第 14 章标题又造出第三种称呼「崔督使」。设计文档 §3 的"既有
  实体短引用编号"尚未实现，名称匹配是唯一锚点。
- **实体重复建卡**：bible 阶段产出带称号前缀的卡（`守灯人旧部首脑·崔衡`、
  `灯灵·阿莹`、`老水手·赵四海`），cast 阶段又建裸名卡，三组双卡。跨阶段同名/
  近似名合并缺失，造成记忆匹配歧义与上下文冗余。
- **周期间提案去重缺失**：术语「记忆耗尽效应」被 1–10 与 11–20 两个周期各提交一次
  并都被接受，产生重复术语卡。
- **记忆进入正文生成路径已验证**：第 11 章 Context Pack 含全部 6 条人物状态与 26 条
  时间线，`selectRecentChapters` 携带近章正文。正文侧记忆链路符合设计。

## 6. 下一步优先级（依本次证据重排）

1. 滚动策划提示词注入封存记忆：上一周期 `expectedClosingState`/`actualClosingState`
   对比、最新人物状态摘要、开放伏笔与时间线尾部（预算受控），否则下一周期规划必然
   与正史漂移；
2. 批次记忆审核硬门禁 + §4 的 payload 容错与提示词修正；
3. 一次低温 JSON 修复调用（§3）；
4. 实体短引用编号 + 跨阶段近似名合并（§5）；
5. 以上稳定后再实现无人值守 Workflow Runner（沿用本评估的无头驱动路径，它已验证
   了 Runner 需要的全部状态机入口）。

## 7. 复现方式

```bash
# 密钥：从系统取回已配置模型 key（与产品 SecretVault 同源），写入 %TEMP%/amy-e2e-key.txt
# 或导出 AMY_E2E_REAL=1 前手动写入该文件，随后：
AMY_E2E_REAL=1 npx vitest run tests/e2e/rolling-cycle.e2e.test.ts
```

数据库落在 `%TEMP%/amy-e2e/rolling-cycle.db`，中断后重跑自动续。密钥文件仅在
本地临时目录，不进入仓库；评估结束后应删除。
