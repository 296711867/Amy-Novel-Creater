# 滚动十章小说 Harness 与版本化记忆

## 1. 目标

长篇小说不再一次生成全部章节标题和章纲。作品先建立可锁定的全书基础，再以默认十章为
一个规划周期循环执行：

```text
作品级基础（步骤 1–6）
  → 全书路线骨架
  → 当前十章策划
  → 前置设定增补提案
  → 作者审核与范围一致性检查
  → 逐章候选正文
  → 接受正文并提交版本化记忆
  → 对比计划结束状态与实际结束状态
  → 调整后续路线并规划下一个十章
```

“自动生成”指 Agent 自动完成分析、策划、正文和记忆提取，不表示模型可以绕过作者或
覆盖锁定设定。未接受正文和未接受提案都不是正史。

## 2. 工作流重定义

步骤 1–6 保持作品级基础：创作目标、核心创意、故事圣经、核心人物、完整人物体系、
场景与故事实体。步骤 7–10 改为可重复的规划周期：

7. **滚动路线与当前十章**：生成全书阶段骨架，并详细规划当前章节范围；
8. **策划包与增补提案审核**：审核标题、章纲、人物、场景、道具、技能和前置设定变更；
9. **当前范围一致性检查**：只检查当前范围，不要求未来所有章节已经详细规划；
10. **当前范围正文生成**：按章生成候选、审查、接受和提交记忆。

第一周期默认 `1–10`，随后为 `11–20`。**范围大小已可配置**：作品级 `cycleSize`
（5–15，默认 10），创建时设置，规划向导第 7 步可中途调整——已开始的批次不受影响，
调整从下一个新批次生效。上限 15 是因为单次规划 JSON 输出随批大小增长，真实模型裸
JSON 失败率在十章时已约 40%（见 `E2E_ROLLING_CYCLE.md`）。

## 3. 全书路线与十章策划包

全书路线只保存阶段/分卷的近似章节范围、目标、主要矛盾、关键转折和预期收束，不生成
全部章节详情。十章策划包必须包含：

- 周期目标、开场状态、高潮和预期结束状态；
- 每章位置、标题、两到四句章纲、视角人物、涉及人物、场景、道具和技能；
- 冲突、结果、伏笔动作与章末钩子；
- 需要新增或补充的前置设定提案。

既有实体在 Prompt 中使用短引用编号，避免同名和别名歧义；新实体使用本周期临时引用，
通过提案后再获得正式 ID。规划结果先作为候选保存，审核后才更新章节槽位。

## 4. 设定变更和锁

设定分四类：

| 类别 | 规则 |
| --- | --- |
| 死设定 | 作者禁忌、核心规则及作者明确锁定字段；数据层拒绝 AI 修改 |
| 核心设定 | AI 只能提交带理由的字段级修改提案 |
| 可扩展设定 | 新配角、场景、道具、技能、势力成员可提交新增提案 |
| 动态状态 | 只由已接受正文更新，不允许规划阶段提前进入正史 |

提案按字段显示旧值、新值和理由。接受提案不会重置整个作品工作流；只有修改作品级锁定
基础才撤销相应全局确认。场景扩展和新人物等周期级补充只影响当前周期检查。

## 5. 版本化小说记忆

记忆分为永久设定、章节记忆、动态正史和临时上下文：

- 永久设定：故事圣经与人物、地点、势力、物品、技能卡；
- 章节记忆：摘要、主要经历、参与实体、状态变化、未解决问题和结尾钩子；
- 动态正史：人物/物品/技能状态、实体关系、时间线和伏笔；
- Context Pack：针对当前章节从前三层按时间和相关性选择的不可变快照。

每条 AI 派生记忆必须记录候选稿、章节版本和来源章节。拒绝候选时对应提案作废；接受
新的章节版本时，旧版本派生记忆失效并触发后续范围复核。下一章只读取当前章节之前、
当前有效版本产生的最新相关状态。

## 6. Context Pack v2

构建章节上下文时先从章题、章纲、场景和视角人物得到相关实体，再沿有效关系扩展一层
道具、技能、势力和人物关系。按以下顺序分配预算：

1. 作者意图、禁忌和当前章节计划；
2. 本章相关实体的永久设定；
3. 截至上一章的最新状态和有效关系；
4. 相关时间线与活动伏笔；
5. 最近三到五章摘要和最近一到两章完整正文；
6. 低优先级远期材料。

首版使用实体引用、名称/别名和 SQLite 查询；需要跨大量章节语义召回且真实评估证明
确定性检索不足时，再增加 FTS 或可选 Embedding。

## 7. 规划运行日志与 JSON 边界

每次规划调用在解析前保存运行记录：阶段、范围、模型、Prompt 哈希、原始响应、Token、
状态、解析错误和重试次数。失败响应可以不再次调用模型而重新解析。

解析顺序为：直接 JSON、JSON 代码块、首个平衡 JSON 对象、Zod 校验。若存在可疑的第二
个 JSON 对象则不得静默忽略。供应商支持时使用结构化输出；结构完整性失败时最多执行
一次低温 JSON 修复调用。任何失败都不能覆盖已确认规划。

## 8. 周期状态机与门禁

```text
planning → proposal_review → plan_review → ready
  → generating → memory_review → completed
  ↘ failed / needs_revision / superseded
```

- 当前范围标题、章纲和实体引用完整后才能进入 `ready`；
- 正文生成接口必须验证对应周期为 `ready` 或 `generating`；
- 周期完成后比较预期和实际结束状态，再创建下一周期；
- 未来章节保留空槽位是正常状态，不再导致全书一致性检查失败。

## 9. 实施顺序

1. 规划运行日志、原始响应保存和可恢复 JSON 解析；
2. 范围化规划 Schema 与十章周期持久化；
3. 步骤 7–10 页面、范围门禁和周期状态机；
4. 字段锁、设定增补提案和审核 Diff；
5. 章节记忆、通用实体状态、实体关系和版本来源；
6. Context Pack v2 和章节改写失效传播；
7. 真实 API 完成一个 `1–10 → 11–20` 闭环；
8. 评估通过后由 Workflow Runner 自动驱动相同状态机。

## 10. 当前实现状态（2026-08-30）

已经落地：

- 规划原始响应、模型、范围、Token、错误和 Prompt 哈希持久化；解析支持代码块、尾随说明
  和平衡 JSON 截取，遇到第二个 JSON 时拒绝静默吞掉；
- 解析边界容错：`profile` 字段的数组/数字值归一为字符串；卷名匹配归一化（模型常把
  阶段范围写进卷名而章节引用裸名）；
- `planning_cycles` 保存当前十章的目标、开场、高潮、预期/实际结束状态；
- 第 7–10 步按当前范围工作，第一批默认 1–10，封存后自动定位下一批；
- 正文批次的 Web/Electron 双入口都校验“范围一致 + 周期 ready/generating”；
- AI 对人物、地点、势力、物品和术语的补充进入 `planning_proposals`，逐项接受或拒绝，
  未接受前不修改正史；实体支持 `profile.locked=true` 整卡锁和 `lockedFields` 字段锁；
- 人物动态状态按章节保存位置、身体、情绪、知识、目标、道具和技能，并进入 Context Pack；
- 接受候选正文后章节状态变为 `accepted`；全部章节接受后，作者填写实际结束状态并封存周期；
- 完整项目包已包含规划日志、周期和设定提案，导入时会重映射作品与周期 ID；
- **真实 API 闭环已跑通**（智谱 GLM-5.2）：1–10 规划 → 正文 → 正史 → 记忆回写 →
  封存 → 11–20 规划 ready，全程由 `tests/e2e/rolling-cycle.e2e.test.ts` 无头驱动
  （`AMY_E2E_REAL=1`），评估报告见 `E2E_ROLLING_CYCLE.md`。

下一阶段（依真实评估证据排序）：
